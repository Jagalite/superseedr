# Native stall characterization

The synthetic fixture reproduces a download that reaches 0.5%, remains connected
without issuing further requests, and completes after pause/resume plus peer
rediscovery. This establishes a possible mechanism, not the cause of the original
live incident: its logs did not record whether an `Unchoke` notification was lost.

The starting branch commit is `0f5f4bbf`. The comparison baseline is remote `main`
at `a83e3909bafe8b543a14699d336396906a533513`.

## Results

All six cases passed on both revisions. The original three single-peer cases
also passed in three earlier branch runs.

| Case | Branch | Main | Recovery connections |
| --- | --- | --- | --- |
| Healthy control | 200/200 pieces | 200/200 pieces | One TCP connection throughout |
| Full inbox, then pause/resume and rediscovery | 1/200 for 97 simulated minutes, then 200/200 | Same | Two TCP connections total |
| Full inbox, then repeat `Unchoke` | 1/200 for 97 simulated minutes, then 200/200 | Same | Original TCP connection throughout |
| Four peers unchoke during the same full inbox | All four remain choked at 1/200 for 97 simulated minutes; repeating one `Unchoke` completes 200/200 | Same | Original four TCP connections throughout |
| Three peers unchoke while full, fourth after drain | Fourth peer completes 200/200 without pause; three remain choked | Same | Original four TCP connections throughout |
| Fresh torrent after shared resource service churn | No retained permits after 128 disconnects; fresh torrent completes through the late fourth peer | Same | 132 warmup connections, then four fresh-torrent connections |

Every completed case independently verified all generated payload bytes. The
same-connection recovery isolates the stale choke state from the other effects
of pause/resume. This loss mechanism is inherited from `main`; these runs do not
establish that the branch makes inbox saturation more likely.

The old `main` tree places native tests in the binary target, so its run used
`--bin superseedr` instead of `--lib`. The copied fixture required only a resource
module import adjustment, visibility for two existing test helpers, and a pause
observer using `activity_message == "Paused"` plus zero connected peers. The older
metrics snapshot leaves `torrent_control_state` at its default while paused.
No production behavior in the baseline was changed.

## Reproduction

The opt-in tests are in `src/torrent_manager/stall_reproduction_tests.rs`. Run:

```sh
SUPERSEEDR_PEER_TRANSPORT=tcp cargo test --locked --offline --lib \
  --features synthetic-load stall_reproduction_ -- \
  --ignored --nocapture --test-threads=1
```

The tests require permission to bind localhost sockets. They use generated data,
a temporary directory, a disabled DHT service, no trackers, and independent
manager/resource/session instances. They do not load the user's configuration,
touch existing downloads, or restart the running application.

The fixture runs the production TCP reader/writer, `PeerSession`, manager event
loop, piece scheduler, hash verification, and native payload storage:

1. A synthetic peer advertises one of 200 pieces. The manager downloads and
   commits it, reaching 0.5%.
2. The peer chokes the client and advertises the remaining pieces. The fixture
   waits until the manager has observed both changes.
3. For the pressure cases, the fixture fills the actual 1,000-slot manager inbox
   with harmless commands and stops polling only the manager. Peers send
   `Unchoke` 10 ms apart, followed by a 50 ms observation interval. The session
   and socket tasks remain runnable throughout.
4. The manager resumes processing and its queue drains completely. The peer is
   now willing to answer every request, but the manager still marks it choked.
5. Keep-alives and repeated availability notifications maintain the connection
   during 97 minutes of accelerated Tokio session/interval time. No more wire
   requests or verified pieces appear. Each clock advance waits for incoming
   peer activity; OS/socket scheduling delays are not treated as peer silence.
6. One case pauses/resumes the manager and explicitly rediscovers the localhost
   peer because this fixture has no discovery service. Another resends `Unchoke`
   over the existing connection without pause/resume.
7. Successful recovery must complete all 200 pieces and independently match all
   3,276,800 generated bytes read back from the temporary payload file.

The four-peer cases send either all four notifications during that blocked
interval, or three during it and the fourth only after the inbox drains. The
all-four case observes the stall for 97 simulated minutes before repeating just
one peer's `Unchoke`. The late-fourth case checks that one useful peer can finish
the payload even while the other three remain incorrectly marked choked.

## Client uptime and connection churn

The reported roughly 30 hours refers to client uptime. The lifecycle case keeps
one shared resource service alive across 32 rounds of four remote disconnects
and reconnections (128 remote disconnects). After every cleanup it checks that
peer-connection, disk-read, and disk-write permits and queued requests are zero.
It distributes the rounds across 30 hours of accelerated Tokio idle time, then
shuts down the warmup torrent manager and starts a fresh manager and payload
directory using the same resource service. The fresh torrent runs the three-lost,
one-late `Unchoke` case.

An initial `main` run failed an immediate post-shutdown permit snapshot: its
manager had returned while four session tasks were still releasing their
permits. The fixture now allows a bounded two-second cleanup window after
shutdown. All permits released in about 3 ms in the follow-up `main` run; this
was asynchronous teardown, not a lasting resource leak. The same bounded check
is used on both revisions.

Startup, disconnects, reconnections, and recovery use real TCP and disk I/O.
Only idle/stall observations accelerate Tokio timers. This is not a real
30-hour client soak: it does not age `std::time`/wall-clock state, run the app UI,
accumulate global peer-policy history, or model external tracker/network
behavior. It checks shared resource cleanup across churn and subsequent use by
a fresh torrent; it cannot exclude other effects of long client uptime.

## Mechanism

`PeerSession` forwards incoming `Choke`, `Unchoke`, and `Interested` notifications
with `try_send`, ignoring a full manager inbox. A lost `Unchoke` leaves the
manager's peer state choked, so `AssignWork` returns without sending requests.
Periodic availability updates do not repair that state. The session has no
requests in flight, so the 20-second outstanding-block timeout does not apply;
continued peer messages also prevent the 120-second inactivity timeout.

The existing full-channel warning in the manager describes the opposite
direction, manager-to-session delivery. Its absence in the live log does not
rule out this session-to-manager loss.

The fixture deliberately injects the queue-pressure condition. It does not prove
that ordinary traffic produced that pressure during the reported live stall.
`[STALL_REPRO]` output records verified pieces, connected/choked peers, wire
requests, control state, and the number of accepted TCP connections. No new
production logging or scheduling behavior is required for this characterization.

These tests are ignored by default because they characterize existing faulty
behavior. A delivery fix should turn the pressure cases into progress assertions,
while retaining the healthy control and checking incoming/outgoing backpressure
and cancellation behavior.

## Session delivery fix validation

The fixture now expects retained unchokes to resume downloading when the manager
inbox drains, without a repeated unchoke or pause/resume. The historical
stall assertions remain available with `SUPERSEEDR_REPRO_EXPECT_DROPS=1` when
replaying the diagnostic against pre-fix source. Existing observations above
describe the pre-fix runs; they are not evidence for the new delivery helper.

The fixed source passed all six TCP cases. With one pressured peer and with all
four peers pressured together, downloads advanced from 1/200 to 200/200 after
the inbox drained, on the original one/four TCP connections. The four-peer case
reported zero peers choked after the pressure interval. The churn case also
completed on its original four fresh-torrent connections. Payload bytes were
verified in every case. This is synthetic evidence, not a live-client soak.

The focused session suite passed 32 tests, including reservation fairness while
flushing outgoing work, startup/control ordering, blocked-wait cancellation and
writer failure, and metadata completion under manager backpressure.

The pressure cases now also wait for each pressured peer identity to become
unchoked, while peers scheduled to unchoke later must still be choked. This
assertion runs before any late notification, so one working peer cannot mask
lost notifications from the others. The fairness test uses immediate receives
after explicitly polling delivery and bounded waits for sends, so a regression
fails instead of leaving the test waiting indefinitely.
